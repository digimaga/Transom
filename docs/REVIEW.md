## 未解決／実機でのブロッカー候補

**P0：macOS 14+の協調アクティベーションとフォーカス取得。** TransomはLSUIElementで、ヘッダーは非アクティブNSPanelのため、`NSRunningApplication.activate()` が拒否される可能性がある。対策として、AXAppWorker.focus内でアプリ要素への `kAXFrontmostAttribute` 設定をアプリ専用ワーカーキュー上で試み（settableのときだけ、失敗しても続行）、その後に既存のkAXRaiseとkAXFocusedWindow設定を行う形に変更した。MenuCoordinator.request、DragCoordinator.begin、AppController.activateの `activate()` は戻り値を成否判定に使わないbest effortへ降格し、非推奨の `.activateIgnoringOtherApps` を削除した。`validateFocus` による厳格な検証は変更しておらず、検証が通らなければメニュー／ドラッグ／前面化は実行されない。

観測した事実は次のとおり。macOS 26（Darwin 25.6）／Apple Silicon／Command Line Toolsのswiftcで、本変更後に `xcrun swift build --product Transom` がエラー0・警告0で完了した（Command Line Toolsの検索パスに関するld警告のみ。コード由来ではない）。一方、(a) `activate(options:)`、(b) `activate(from:options:)`、(c) AX `kAXFrontmost`＋kAXRaise の実機比較プローブは、コンパイルには成功したが、作業環境の実行許可により起動できず**未計測**である。`AXIsProcessTrusted()` の値も未計測。したがって、本機でどの経路が実際に前面化を達成するかは確認できていない。TCCやシステム設定の変更は行っていない。

**解消（2026-09-16）：Macでのコンパイル。** macOS 26（Darwin 25.6）／Apple Silicon／Command Line Tools（Swift 6.4、Xcode未インストール）で `bash scripts/verify.sh` を実行し、Transom・TransomLabの型チェックとリンク、共通ロジック34件のテストが成功した。SDK差分による型エラーは発生しなかった。唯一の修正点はXCTestがCommand Line Toolsに含まれないことで、テストをSwift Testingへ移行した（`docs/VALIDATION.md`）。`--capabilities` は `exact-window-id=true`、`private-relative-ordering=true` を返した。これはコンパイルと関数の存在確認であり、GUI動作の合格ではない。

**一部解消（2026-09-17）：WindowServerとの実際の並び順。** macOS 26／Apple Siliconで実機確認した。透明パネルはCGの `optionOnScreenOnly` 一覧に含まれ、`OrderingPolicy.isSafe` のメタデータ照合が機能し、バーは対象窓の直前へ正しく表示された（前面の別アプリ窓が両者より前のとき背面窓のバーが浮かないことも確認）。ただし非公開経路（SkyLightのSLSTransactionSetWindowLevel）はこのOSでコード -5（setLevel失敗）を返し使えなかった。CGErrorの戻り値も正規のコードではなく、ABIが想定と異なる。現在は3回失敗した時点で非公開経路を自動停止し、以後は公開相対order＋メタデータ照合のみで動作する（バー表示は正常）。多数窓・複雑な重なりでの網羅確認とSkyLight ABIの精査は未完了。

**解消（2026-09-17）：Stage Managerのサムネイルにバーが付く。** Stage Managerを有効にすると、左ストリップに縮小された窓のAXフレームは元のサイズのまま（例：586×488）で、CGの実フレームだけがサムネイルサイズ（82×105）になる。適格判定はAXフレーム、配置はCGフレームで行っていたため、幅82ptの小さなバーがサムネイルの上に表示された。対策として `Geometry.isEligibleSize`（幅280・高さ120以上）をCoreに置き、走査時のAXフレームと描画時のCGフレームの両方に適用した。修正後は中央の窓だけにバーが付き、サムネイル切替にも追従する。

**解消（2026-09-17）：バーがウィンドウにぴったり追従しない。** 元のタイトルバーでのドラッグではバーが最大84pt遅れ、離してから0.5秒後にやっと一致し、外付けバーのドラッグでは窓側が離してから0.6秒後まで動き続けた。原因は3つ。(1) バー位置の更新がCGメタデータの50ms周期（操作後は0.5秒周期）に縛られていた。(2) バーのドラッグは1ステップごとに約14回のAX往復で完全検証し、同じキューのAX走査にも待たされていた。(3) 背景キューのCGWindowList呼び出しが自プロセスのCAトランザクション完了待ちで接続ロックを握り、メインスレッドのコミットと相互待ちになって0.5秒止まっていた。対策として、マウス操作中だけ対象窓の枠を4ms周期で読んでバーを直接置くFrameTrackerを追加し、バーのドラッグでは移動直後に読み戻した実枠へバーを置き、ステップ間の検証を「正確なID＋フォーカス窓一致」に絞って完全検証は0.25秒ごとにし、ドラッグ中は対象アプリの走査を止め、メタデータ読み取りをメインスレッド＋ `CATransaction.flush()` 後へ移した。安全条件（正確なID、フォーカス検証、前後順の照合、空間不足時の非表示）は変更していない。数値は `docs/ACCEPTANCE.md` P1-01・P1-02と `docs/VALIDATION.md`。

**解消（2026-09-17）：NSMenu追跡中に追従・取消が止まる。** メニューを開いている間、タイマー（tick）は動くのに `render` が一度も走らず、対象窓を閉じてもメニューが残り、他窓のバーも旧位置に留まった。診断ログで、`DispatchQueue.main.async` で運んでいたワーカーとメタデータ読み取りの完了通知がNSMenuの追跡ループ中は配送されないことを確認した（メニューを閉じた直後にmetadataAge約6.5秒でrenderが再開）。対策として `MainRunLoop.perform`（`RunLoop.main.perform(inModes: [.common])` ＋ `CFRunLoopWakeUp`）を追加し、AXAppWorker.submit、WindowServer.read、AXObserverHubの配送をそれへ切り替えた。修正後はメニュー表示中も他窓のバーが0.5秒以内に追従し、対象窓のクローズや別アプリ切替から0.25秒以内にメニューが閉じる。実行拒否自体は修正前から機能していたが、UI上の残存が解消した。

**解消（2026-09-17）：NSAlertのシートを検知できない。** macOS 26ではNSAlertのシートが窓の `AXSheets` 属性に現れず（0件）、子要素の `AXSheet` としてのみ現れるため、`modal` 判定をすり抜けてシート表示中もバーが残った。`AX.hasSheet` で子要素（先頭16件）の役割も確認するようにし、走査と `validateFocus` の両方で使う。修正後はシート表示中にバーが消え、閉じると復帰する。

**解消（2026-09-17）：Chromium/Electron系アプリでの「フォーカス確認不可」。** Claude（Electron）の外付けバーからメニューを開くと、`validateFocus` が0.6秒以内に通らず拒否された。理由コードを記録する診断（`AXAppWorker.lastFocusMismatch`、`focus` カテゴリのログ。文書名等は含まない）を追加して特定したところ、Chromium系アプリが前面のときシステム全体の `AXFocusedApplication` が値を返さない（nil）ことが原因だった。対策として `AXAppWorker.frontmostPID()` を追加し、AXが無回答（nil）のときに限り `NSWorkspace.frontmostApplication` を前面判定に使う。AXが別PIDを返す場合は従来どおり不一致として拒否し、対象窓のAXFocusedWindow一致・ウィンドウID一致・役割・状態の検証は変更していない。`validateWitness`（文脈の再照合）とメニュー見出しの照合にも理由コードのログを追加した。修正後、Claudeのメニューが無効項目のグレー表示を含めて正しく展開した。Chrome・Safari等の他のChromium/WebKit系アプリでの再確認は未実施。

**解消（2026-09-17）：NSMenu前後のフォーカスとメニュー実行の対象一致。** TransomLabの同名2窓で確認した。A窓のバーのコピーでクリップボードにA窓の行が入り、A窓のバーの検証保存で `window=A`、B窓のバーの検証保存で `window=B` が記録された。各バーは自分の対象窓に対してのみ作用し、取り違えは観測されなかった。なお対象窓が他窓に隠れてメニューボタンを押せない状況では操作が無反応（実行されない安全側）になる。

**P0：NSMenu前後のフォーカス。** 同名2窓、選択テキスト、保存で、元アプリの選択状態が残り、コマンドが適切な窓へ作用するかを確認する。メニューを閉じる際のフォーカス復帰や動的な有効状態の扱いにアプリ差がある。厳密な参照照合が正当な操作も拒否する可能性がある。

**P1：同じSpaceでのMission Control、Stage Manager。** これらの開始・終了を完全には検知していない。バーだけ残る・ずれる・ちらつく可能性がある。現状を「対応済み」として配布しない。

**P1：動的・大規模メニュー。** 取得予算・深さ・件数に上限があり、遅延生成、Option代替、特殊なServices/Help UI、独自描画は欠落や無効表示になり得る。元のメニューを利用可能なまま残す。

**P1：多数のウィンドウでの負荷・取得順。** 多数のAXウィンドウを持つアプリでは読み取り予算に達し、一部のバーが隠れる可能性がある。処理時間・飢餓・メモリー・CPUは実測して調整する。イベント駆動だから低負荷だと保証しない。

**P1：完全な誤操作排除は保証できない。** 検証からAXPressまでの間にも対象プロセスは動く。原子的な文書指定実行APIではない。コードは不確実な状態を拒否するが、「どの状況でも100%誤操作なし」と記載しない。

**P1：配置操作は非原子的。** サイズの変更が成功して位置変更が失敗すると、サイズ変更だけ残る場合がある。元へ強制復帰して、その後のユーザー操作を上書きしない。

**P2：公開配布。** このパッケージは開発用。利用規約、アクセシビリティ体験の追加監査、Developer ID署名・公証、インストーラー、自動更新などは作っていない。

## レビュー結論

実機での開発を引き継げるコード一式と検証手段を用意した。設計の主要な矛盾は修正したが、Mac固有の2大要所（並び順・メニューのフォーカス）を合格扱いにはしていない。次の判断材料は追加の机上説明ではなく、Mac上のコンパイル結果と `ACCEPTANCE.md` の操作記録である。
