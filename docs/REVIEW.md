## 未解決／実機でのブロッカー候補

**P0：macOS 14+の協調アクティベーションとフォーカス取得。** WindowBarはLSUIElementで、ヘッダーは非アクティブNSPanelのため、`NSRunningApplication.activate()` が拒否される可能性がある。対策として、AXAppWorker.focus内でアプリ要素への `kAXFrontmostAttribute` 設定をアプリ専用ワーカーキュー上で試み（settableのときだけ、失敗しても続行）、その後に既存のkAXRaiseとkAXFocusedWindow設定を行う形に変更した。MenuCoordinator.request、DragCoordinator.begin、AppController.activateの `activate()` は戻り値を成否判定に使わないbest effortへ降格し、非推奨の `.activateIgnoringOtherApps` を削除した。`validateFocus` による厳格な検証は変更しておらず、検証が通らなければメニュー／ドラッグ／前面化は実行されない。

観測した事実は次のとおり。macOS 26（Darwin 25.6）／Apple Silicon／Command Line Toolsのswiftcで、本変更後に `xcrun swift build --product WindowBar` がエラー0・警告0で完了した（Command Line Toolsの検索パスに関するld警告のみ。コード由来ではない）。一方、(a) `activate(options:)`、(b) `activate(from:options:)`、(c) AX `kAXFrontmost`＋kAXRaise の実機比較プローブは、コンパイルには成功したが、作業環境の実行許可により起動できず**未計測**である。`AXIsProcessTrusted()` の値も未計測。したがって、本機でどの経路が実際に前面化を達成するかは確認できていない。TCCやシステム設定の変更は行っていない。

**解消（2026-09-16）：Macでのコンパイル。** macOS 26（Darwin 25.6）／Apple Silicon／Command Line Tools（Swift 6.4、Xcode未インストール）で `bash scripts/verify.sh` を実行し、WindowBar・WindowBarLabの型チェックとリンク、共通ロジック34件のテストが成功した。SDK差分による型エラーは発生しなかった。唯一の修正点はXCTestがCommand Line Toolsに含まれないことで、テストをSwift Testingへ移行した（`docs/VALIDATION.md`）。`--capabilities` は `exact-window-id=true`、`private-relative-ordering=true` を返した。これはコンパイルと関数の存在確認であり、GUI動作の合格ではない。

**一部解消（2026-09-17）：WindowServerとの実際の並び順。** macOS 26／Apple Siliconで実機確認した。透明パネルはCGの `optionOnScreenOnly` 一覧に含まれ、`OrderingPolicy.isSafe` のメタデータ照合が機能し、バーは対象窓の直前へ正しく表示された（前面の別アプリ窓が両者より前のとき背面窓のバーが浮かないことも確認）。ただし非公開経路（SkyLightのSLSTransactionSetWindowLevel）はこのOSでコード -5（setLevel失敗）を返し使えなかった。CGErrorの戻り値も正規のコードではなく、ABIが想定と異なる。現在は3回失敗した時点で非公開経路を自動停止し、以後は公開相対order＋メタデータ照合のみで動作する（バー表示は正常）。多数窓・複雑な重なりでの網羅確認とSkyLight ABIの精査は未完了。

**解消（2026-09-17）：NSMenu前後のフォーカスとメニュー実行の対象一致。** WindowBarLabの同名2窓で確認した。A窓のバーのコピーでクリップボードにA窓の行が入り、A窓のバーの検証保存で `window=A`、B窓のバーの検証保存で `window=B` が記録された。各バーは自分の対象窓に対してのみ作用し、取り違えは観測されなかった。なお対象窓が他窓に隠れてメニューボタンを押せない状況では操作が無反応（実行されない安全側）になる。

**P0：NSMenu前後のフォーカス。** 同名2窓、選択テキスト、保存で、元アプリの選択状態が残り、コマンドが適切な窓へ作用するかを確認する。メニューを閉じる際のフォーカス復帰や動的な有効状態の扱いにアプリ差がある。厳密な参照照合が正当な操作も拒否する可能性がある。

**P1：同じSpaceでのMission Control、Stage Manager。** これらの開始・終了を完全には検知していない。バーだけ残る・ずれる・ちらつく可能性がある。現状を「対応済み」として配布しない。

**P1：動的・大規模メニュー。** 取得予算・深さ・件数に上限があり、遅延生成、Option代替、特殊なServices/Help UI、独自描画は欠落や無効表示になり得る。元のメニューを利用可能なまま残す。

**P1：多数のウィンドウでの負荷・取得順。** 多数のAXウィンドウを持つアプリでは読み取り予算に達し、一部のバーが隠れる可能性がある。処理時間・飢餓・メモリー・CPUは実測して調整する。イベント駆動だから低負荷だと保証しない。

**P1：完全な誤操作排除は保証できない。** 検証からAXPressまでの間にも対象プロセスは動く。原子的な文書指定実行APIではない。コードは不確実な状態を拒否するが、「どの状況でも100%誤操作なし」と記載しない。

**P1：配置操作は非原子的。** サイズの変更が成功して位置変更が失敗すると、サイズ変更だけ残る場合がある。元へ強制復帰して、その後のユーザー操作を上書きしない。

**P2：公開配布。** このパッケージは開発用。利用規約、アクセシビリティ体験の追加監査、Developer ID署名・公証、インストーラー、自動更新などは作っていない。

## レビュー結論

実機での開発を引き継げるコード一式と検証手段を用意した。設計の主要な矛盾は修正したが、Mac固有の2大要所（並び順・メニューのフォーカス）を合格扱いにはしていない。次の判断材料は追加の机上説明ではなく、Mac上のコンパイル結果と `ACCEPTANCE.md` の操作記録である。
