# 実装アーキテクチャ v0.5

## 1. コードと責務

|場所|責務|
|---|---|
|WindowBarCore|座標、外付け配置、狭幅レイアウト、世代付きID、Z-order判定、実行許可、存在状態。Foundationのみ|
|WindowBarBridge|_AXUIElementGetWindowとSkyLightの任意の関数をdlsymで読み込むC境界|
|AppController|MainActor。起動、権限、アプリ一覧、状態集約、表示、停止、ユーザーが許可した配置操作|
|AXAppWorker|アプリ1つにつき1つのシリアルキュー。AXオブジェクト、監視登録、スナップショット、フォーカス、位置変更|
|AXMenuStore|同じキュー内でメニュー参照を保持。読み取り、セッション、検証、AXPress|
|WindowServer|CGのメタデータ（窓ID一覧と他プロセス窓の記述）をメインスレッドで読む。描画順の操作もMainActor。FrameTrackerはマウス操作中だけ対象窓の枠を毎秒240回読む|
|HeaderPanel / HeaderView|非アクティブNSPanel、アプリ名・メニューボタン・省略表示・ドラッグ面・右端のウィンドウボタン（最小化・最大化・閉じる）。本文の上に重ねない。パネルは対象窓の直後（背面）に並び、30ptのバーの下に窓と同じ幅で48ptの不透明な帯が続く。帯は前面の窓に隠れ、窓の角丸から透けて見える部分だけがバーとの隙間を埋めるので、角丸の半径（標準窓16pt、Safari約30pt）に依存しない|
|MenuCoordinator|対象のアクティブ化、NSMenuの表示と取消、閉じたあとの実行要求|
|DragCoordinator|対象のドラッグ。書き込みは常時1件まで。最新の座標を優先|
|WindowBarLab|別プロダクト。完全同名の2窓でコピー・保存・シートを検証するフィクスチャ|

依存パッケージなし。Macのみアプリ2本とCブリッジをビルドし、LinuxではCoreとテストのみをビルドする。macOS deployment targetは14、優先実機検証は26／Apple Silicon。Swift 6ツールチェーンでSwift 5言語モードを明示。AXUIElementを根拠なくSendableにする設計にはしていない。

## 2. ウィンドウの同定

WindowToken = processInstance(UUID) + pid + CGWindowID + incarnation。

NSWorkspaceで観測したプロセスの一生ごとにinstanceを割り当てる。既存の同じCGWindowIDでもAX参照が変わればincarnationを更新する。AXWindowとCGWindowIDを正確に結べない窓は扱わない。幾何学的一致やタイトル一致へのフォールバックはない。

AX側が存在・属性の主な情報源で、CG側は現時点の表示・位置・描画順を補完する。完全なAX一覧で2回続けて不在なら削除、1回目は隠す。一時的エラーや読み取り期限超過は不確実性として扱い、存在していた全窓を削除しない。取得から4秒以上古い情報で操作を受け付けない。

## 3. UIと配置

1段・高さ30ポイント。左から、アプリアイコンとアプリ名ボタン、実際のメニュー名（左揃え。幅不足時は `»`）、残り幅を使うドラッグ領域（窓を動かす面。文書名は表示せず、ツールチップにだけ「アプリ名 — 文書名」を出す。窓のタイトルバーやアプリのタブに名前があるため）の順。アプリ名ボタンからアプリメニューを開く。右端にWindows風のウィンドウボタン3つ（最小化・最大化・閉じる、各40pt）を置く（2026-09-17にユーザーの要望で「重複実装しない」方針を改めた。Mac本来の3色ボタンはそのまま残る）。

ウィンドウボタンの実装：最小化と閉じるは、正確なIDで一致した窓要素の `AXMinimizeButton`／`AXCloseButton` をOperationPermit経由で1回だけAXPressする（標準窓・非モーダル・シートなしを確認。cannotCompleteは「実行されたか不明」として再試行しない。閉じる前の確認は元アプリの未保存ダイアログに任せる）。最大化は、フォーカス検証のうえ `Geometry.maximizedFrame`（使用可能領域からバーの高さを除いた枠）へ位置・サイズを設定し、もう一度押すと記録しておいた元の枠へ戻す。これは規則1の「明示した操作」に当たる。元の枠の記録はプロセス内だけで、窓の消滅・再起動で失われる。アプリが配置を補正した場合は失敗として報告し、勝手に再試行しない。

標準は完全な外付け。使用可能な画面領域の上下にバーの高さ分が入らなければ（メニューバー直下など）隠す。窓が画面の左右・下へはみ出している場合はバーも窓と同じx・幅で追従し、画面外の部分は窓と同じく切れて見える（2026-09-17に変更。それ以前はバー全体が画面内に入らないと隠していた）。元のウィンドウを自動で押し下げたり、タイトルバーを覆ったりしない。ユーザーがWBの「最前面の1枚にバー用の空間を確保」を押した場合だけ、位置・サイズを検証してその1枚を調整する。サイズと位置の設定は非原子的であり、途中失敗時に部分的な変更が残る可能性がある。勝手なロールバックで後のユーザー操作を上書きしない。

座標は、プライマリ画面の左上を原点とする論理ポイントに統一。AppKitのNSScreen.mainではなくNSScreen.screens.firstを基準に反転する。左右だけでなく、上下に配置したディスプレイと負座標をCoreのテスト対象にしている。Retinaのピクセル数はレイアウトへ混ぜない。

## 4. Z-orderとSpaces

NSPanelのフローティングレベルは使わない。通常レベルに限定し、対象を指定したAppKitの相対order（`order(.below, relativeTo:)`）で対象の直後（背面）へ並べる。バー本体は窓の外にあるので背面でも見え、帯は窓に隠れる。SkyLightのトランザクション（WBOrderAboveWindow）は前面へ並べるものでmacOS 26では失敗もしたため使わない。移動・レベル変更の対象は自分のバーだけ。元アプリのWindowServer設定を変更しない。

並べ替えの戻り値を成功の証明にしない。最初は透明・クリック無効で並べ、CGの前後順で「対象が自分より前にあり、両者の間にバーへ重なる他窓が挟まっていない」ことを照合してから表示・入力を有効にする（`OrderingPolicy.isDirectlyBehind`）。自分が対象より前にあると帯が対象のタイトルバーを覆うので、その状態では表示しない。この照合には帯を含むパネル全体の枠を使う。「クリック無効」は `ignoresMouseEvents` ではなく、内容ビューを隠して不透明画素を無くすことで実現する。WindowServerは非不透明窓の透明画素へのクリックを下の窓へ渡すが、`ignoresMouseEvents` を一度でもfalseに設定するとその窓は枠全体で入力を受けるようになり元に戻せない（macOS 26.6で確認）。メタデータの遅延や実際の描画との競合は残るので実機検証が必要。

Spacesは真の所属複製ではない。外付けパネルを複数Spaceに参加可能にし、その時点で画面上に確認できた対象に限って表示する。Space変更通知と画面構成変更時は全バーを隠し、短い猶予のあと再照合する。Mission Controlが同じSpace内で開かれた場合を完全に検知する仕組みはない。Stage Managerとともに実機での残存・ちらつき検証が未完了。ネイティブフルスクリーンはAX状態と全画面相当の形状から除外する。

## 5. メニュー処理

メニュー名は固定しない。アプリのAXMenuBarを取得し、トップ見出しだけを低頻度で更新する。クリック時に対象ウィンドウをアクティブ化し、その窓が実際の操作対象になったことを確認してから子項目を読む。

メニューUIはNSMenuに修正した。非アクティブパネル内に表示し、キーボード移動、Esc、階層、チェック表示を標準機構に任せる。元のショートカットはラベルとして表示するだけで、WindowBarのresponder chainには登録しない。メニューを閉じる前には元アプリのコマンドを発火しない。

実行時に、ウィンドウ世代、前面PID、AXFocusedWindow、標準窓・非モーダル状態、文書タイトル・AXDocument（取得できる場合）、フォーカス中のUI要素、選択範囲（取得できる場合）を再照合する。さらにAXMenuBarからの全経路をたどり、各段のインデックス・AX参照・役割・タイトル、最終項目の有効状態とAXPress対応を確認する。文字列検索や「似た項目」への再解決はしない。

最後にOperationPermit.commitOnceを通してAXPressを1回だけ送る。AXの成功は要求受理であり、保存完了の保証ではない。cannotCompleteは「実行されたか不明」。自動再試行しない。クロスプロセスの確認と実行は原子的ではなく、最後の確認後に外部アプリの状態が変わる競合を完全には消せない。

動的・遅延生成されたサブメニューを無理にAXPressして元のメニューを開く操作はしない。取得できない項目は無効表示にする。Optionキーによる別項目や独自UIの完全再現は範囲外。

## 6. 応答性と停止

AXはアプリごとに独立したGCDシリアルキュー。全アプリを1つのキューへ直列化しない。コピー・実行を含むAXメッセージはMainActorで送らない。MainActorでは権限の確認などローカルなAPIだけを呼ぶ。

通常はAX通知＋1.5秒程度の状態照合。CGメタデータ（前後順の照合用）は通常0.5秒、マウスボタン押下中・バーのドラッグ中とその後0.3秒、および並び替え直後の再確認中は20回/秒で取得する。これとは別に、マウス操作中だけFrameTrackerが前面アプリの窓とドラッグ対象の枠を4ms周期で `CGWindowListCreateDescriptionFromArray` で読み、バーの位置だけを即座に合わせる（前後順・適格性の判定は通常の照合に任せる）。バーのドラッグでは、AXで窓を動かした直後に読み戻した実際の枠へバーを置く。1回の移動は「正確なID＋フォーカス窓一致の確認→位置設定→枠の読み戻し」の数回のAX往復に抑え、完全な検証（役割・最小化・シート等）は開始時と0.25秒ごとに行う。ドラッグ中は対象アプリのAX走査（タイトル・メニュー等）を止め、同じシリアルキューで移動を待たせない。

CGWindowListの各呼び出しは、自プロセス接続の直前のCoreAnimation／SkyLightトランザクション（バーの移動・並び替え）の完了を接続ロックを握ったまま待つ。これを背景キューから呼ぶと、メインスレッド側の次のコミット（同じロックが必要）と相互に待ち、0.5秒のタイムアウトまで両方が止まる（macOS 26.6で実測。ドラッグ終了時にバーと窓が0.5秒固まる原因だった）。このため読み取りはメインスレッドで、`CATransaction.flush()` で保留コミットを確定させてから行う。自分のパネルは順序だけID一覧から取り、記述は取得しない。100窓時のCPU負荷は未再測定。AXの1メッセージのタイムアウトは0.16秒を初期値とし、窓一覧0.85秒・メニュー1.2秒等の予算を付ける。これは各メッセージ間での予算確認であり、OSが内部でブロックした呼び出しを強制終了するものではない。

停止、ロック、スリープ、世代交代、メニュー取消では、ロック付き許可オブジェクトを同期的に無効化する。遅れて返ったスナップショットはepoch/instanceが異なれば適用しない。すでにOSへ送ったAXPressは取り消せない。

## 7. 権限・データ

アクセシビリティ許可が基本。画面録画、Apple Events、グローバルなキーボードフックは使わない。CGWindowNameも使わず、タイトルはAXから得る。ネットワーク通信なし。WindowBar本体は文書を書き換えず、元アプリに選択された操作を依頼する。文書名・URLは操作中のメモリーに保持するが、診断出力・ログ・送信には含めない。

WindowBarLabだけはユーザーが「検証保存」を選ぶと専用のApplication Support/WindowBarLab以下へ検証用データを書き込む。製品本体とは別プロダクトであり、通常のビルドには同梱しない。
